# Scan Camera Experience Overhaul

**Date:** 2026-07-14
**Status:** Approved
**Scope:** Redesign ScanScreen's packaged-product capture flow (barcode → nutrition label → front label) to remove the manual "arm next photo" tap that causes a shutter/chip layout collision, add tap-to-focus and pinch-to-zoom, and give the step indicator a sliding-highlight animation.

## Problem

The three-photo capture flow (barcode, optional nutrition label, optional front label) requires an explicit "Add Nutrition Photo" tap before the shutter does anything meaningful for step 2 (`ScanScreen.tsx:632-633` dispatches `ADD_NUTRITION_PHOTO`/`ADD_FRONT_PHOTO`, which the reducer only accepts from `BARCODE_LOCKED`/`STEP2_CONFIRMED` — `scan-phase-reducer.ts:69-85`).

That secondary button collides with the shutter button. `ProductChip`'s root style (`ProductChip.tsx:331-332`, `position: absolute, bottom: 0`) has no `zIndex`. The bottom controls row (`ScanScreen.tsx:576-598`, containing the shutter) is also `position: absolute, bottom: 0` but explicitly sets `zIndex: 10` (`ScanScreen.tsx:915`). In React Native, an explicit `zIndex` wins paint order regardless of JSX order, so the shutter's `Pressable` physically sits on top of the chip's "Add nutrition photo (Optional)" row whenever that row renders near the bottom edge — confirmed against a device screenshot during brainstorming.

The functional consequence is worse than a visual glitch: tapping in the covered area hits the shutter, not the chip button. `onShutterPress`'s guard clause (`ScanScreen.tsx:350-357`) only allows `STEP2_CAPTURING`, `STEP3_CAPTURING`, or `HUNTING` through — `BARCODE_LOCKED` isn't in that set, so the function returns immediately and `takePicture()` is never called. It's a dead tap, not a wasted capture. Users never reach the nutrition-photo step; they eventually bail via "Looks right," which reads as "the flow left the scan screen" even though barcode-to-step-flow navigation is otherwise working as designed.

Separately, there is no tap-to-focus or pinch-to-zoom anywhere in the camera stack — confirmed via full-tree grep, not disabled/dead code, a genuine capability gap versus a standard camera app.

## Solution

| Decision                                     | Choice                                                           | Rationale                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Arming the next capture                      | Automatic, not tap-gated                                         | Removes the friction entirely and eliminates the competing tap-target that caused the collision — a structural fix, not a relayout                                                                                                                                                                                                                                                                          |
| Shutter capture control                      | Stays manual (shutter tap) for all 3 photos                      | Confirmed with user — no hands-free/auto-fire; same physical control throughout, just no separate "arm" step first                                                                                                                                                                                                                                                                                          |
| Post-capture behavior                        | Brief (~1s) auto-advancing preview, tappable to intervene        | Middle ground between "no chance to catch a bad OCR read" and reintroducing a required confirm tap                                                                                                                                                                                                                                                                                                          |
| Post-capture behavior — screen reader active | Suppress the auto-advance timer; require an explicit confirm tap | The ~1s budget assumes sighted-user reaction speed (glance, decide, tap). It doesn't hold for VoiceOver/TalkBack's hear-announcement-then-locate-then-act loop — timing it out on that user class isn't a real "chance to intervene." Matches this file's existing `reducedMotion` precedent (`useAccessibility()`, `ScanScreen.tsx:87`) of branching timing/motion behavior on an accessibility preference |
| Step indicator                               | Sliding highlight bar (position/width animates)                  | Replaces static three-dot color-change; matches "premium and unhindered" feel                                                                                                                                                                                                                                                                                                                               |
| Focus                                        | Custom tap gesture + `focusTo()` + custom animated ring          | Full control over ring timing tied to the focus promise, vs. native gesture's silent (no visual feedback) behavior                                                                                                                                                                                                                                                                                          |
| Zoom                                         | Pinch gesture → Reanimated `SharedValue` → `<Camera zoom={...}>` | Native-thread updates, no JS bridging lag; confirmed VisionCamera v5 supports `SharedValue` directly (`Camera.d.ts:90`)                                                                                                                                                                                                                                                                                     |
| Liquid/solid AI nutrient labeling            | Out of scope, separate spec                                      | Server-side AI/prompt concern, not camera UI — user's explicit call                                                                                                                                                                                                                                                                                                                                         |

## Architecture

### State machine (target behavior)

```
Today:                                          Target:
BARCODE_LOCKED                                  BARCODE_LOCKED (auto-armed for nutrition)
  --[tap "Add Nutrition Photo"]-->                 --[shutter tap]--> capture
  STEP2_CAPTURING                                  --[~1s auto-advance, tap to edit]-->
  --[shutter tap]--> STEP2_REVIEWING               STEP2_CONFIRMED (auto-armed for front)
  --[tap "Confirm"]--> STEP2_CONFIRMED                --[shutter tap]--> capture
  --[tap "Add Front Photo"]-->                        --[~1s auto-advance, tap to edit]-->
  STEP3_CAPTURING ...                                 SESSION_COMPLETE
```

`ADD_NUTRITION_PHOTO`/`ADD_FRONT_PHOTO` stop being user-dispatched actions gated on a button tap and become transitions fired automatically the instant the prior phase resolves. Whether this collapses `STEP2_CAPTURING`/`STEP3_CAPTURING` into `BARCODE_LOCKED`/`STEP2_CONFIRMED` outright, or keeps them as distinct phases entered via an effect-driven auto-dispatch, is an implementation-plan decision — not spec-level. The auto-advance timer (~1s, cancelable by a tap) belongs in the component as a `useEffect`/timeout, not embedded in the pure reducer.

At all times, "Looks Good"/"Looks right" (`CONFIRM_PRODUCT`) remains available as a secondary action to skip remaining optional steps early — this part of the reducer is unchanged.

## Component Details

**StepPill sliding indicator.** A single Reanimated shared value (0/1/2 for Barcode/Nutrition/Front) drives an absolutely-positioned bar's `left`/`width` via `withTiming`, layered behind the three text segments — replaces the current per-dot scale/ring animation as the primary "which step am I on" signal. Existing checkmark-on-complete and connector color interpolation stay.

**Tap-to-focus.** A `Tap` gesture (react-native-gesture-handler) wraps the camera preview. On tap: show `FocusRing` at the tap coordinates, call `cameraRef.current.focusTo({x, y})` (VisionCamera v5, confirmed at `Camera.d.ts:34`). Ring animates in immediately, then settles/fades when the returned promise resolves; VisionCamera's own `autoResetAfter` (default 5s) handles focus lock expiry. The ~1s post-capture review (below) replaces the live feed with the captured photo, so this gesture and the review's "tap to intervene" gesture never compete for taps on the same live surface — the camera preview (and therefore focus-tappability) simply isn't present during that window.

**Pinch-to-zoom.** A `Pinch` gesture drives a `SharedValue<number>` clamped to the active `CameraDevice`'s min/max zoom, passed to `<Camera zoom={zoomValue}>`. An ephemeral zoom-level pill (e.g. "1.8x") fades in during the gesture, fades out ~600ms after it ends. Occupies the previously-unused spacer slot at rest (`ScanScreen.tsx:597`).

**Shutter armed state.** Style (opacity/glow) driven by `scanPhase.type` — full "armed" treatment whenever tapping it is the expected next action (barcode-locked, nutrition-armed, front-armed), so it's never ambiguous whether a tap does something.

**scanCount badge fix.** Currently `position: absolute, top: 120` (`ScanScreen.tsx:953-961`), independent of `topOverlay`'s actual rendered height (safe-area inset + close button + StepPill), so it overlaps StepPill on devices with larger insets — confirmed on-device. Fix: fold it into `topOverlay`'s flex column instead of independently positioning it, so it can't collide with sibling content again.

## Out of Scope (Future)

- Liquid-vs-solid AI nutrient labeling (separate spec — server-side `photo-analysis.ts` prompt/parsing concern)
- BatchScan / ReceiptCapture / CookSessionCapture camera screens — not touched by this design
- Manual exposure control (`exposureBias` is available on VisionCamera v5 if wanted later)
- Hands-free/auto-fire capture for steps 2/3 — explicitly rejected; shutter stays manual

## Testing Strategy

- Unit tests for the reshaped reducer: auto-arming transitions fire correctly from `BARCODE_LOCKED`/`STEP2_CONFIRMED`, `SESSION_COMPLETE`/`CONFIRM_PRODUCT` (skip) paths unaffected
- RTL/fake-timer unit test for the auto-advance effect: fires ~1s post-capture, cancels cleanly on tap, doesn't double-fire on rapid re-capture. This is component-level JS with no native dependency, so it's unit-testable like the reducer above — it does not fall under the focus/zoom carve-out below
- Render-level test asserting the shutter and `ProductChip` never overlap in layout (regression guard for the root-cause bug)
- `scripts/__tests__/worklet-directive-guard.test.ts` run against the new `useCameraFocusAndZoom.ts` hook and both `CameraView` platform variants. This is a required check, not optional: a gesture worklet calling a function imported from another module without its own `"worklet"` directive passes `tsc`/ESLint/unit tests cleanly but silently closes the app in release/OTA builds (`docs/rules/react-native.md:16`) — exactly the failure class this spec's new gesture code is exposed to, and exactly what "verified manually via OTA" (below) would surface only as an unexplained crash, not a caught error
- Focus/zoom gesture _behavior_ (does the ring appear at the right spot, does zoom feel smooth) is native-gesture-driven and not meaningfully unit-testable — verified manually on a physical device via OTA update, consistent with current camera-work verification practice (no dev-client build exists on this machine)
- Manual VoiceOver/TalkBack pass confirming the new review variant announces correctly and the screen-reader path (explicit confirm tap, no auto-advance timeout) behaves as specified
