# Client State Rules

- All server communication goes through `apiRequest()` from `@/lib/query-client` — never raw `fetch()` in components or hooks. Auth tokens travel in the `Authorization` header — never cookies.
- After an irreversible server mutation (account delete, payment, hard-delete), wrap local cleanup (`tokenStorage.clear`, `AsyncStorage.removeItem`) in try/catch and never throw — a post-success error makes the user "retry" a destructive action that already succeeded.
- **`apiRequest` error contract**: it runs `throwIfResNotOk`, so it ALWAYS throws `ApiError("<status>: <serverBody>", code)` on a non-ok response. So (a) an `if (!res.ok)` guard after `await apiRequest(...)` is unreachable dead code that silently kills its branch; (b) `error.message` is the raw server body (prefixed `"404: …"`) — never render it or announce it, show static user-safe copy; (c) branch on `error instanceof ApiError && error.code === "<CODE>"`, never on `error.message`; for status-specific UX return a _specific_ `ErrorCode` server-side, never the generic `VALIDATION_ERROR`. See `docs/solutions/logic-errors/dead-apirequest-guard-hides-broken-error-branch-2026-05-31.md`, `docs/solutions/conventions/apierror-code-driven-static-copy-2026-05-31.md`.
- The centralized 401→logout interceptor fires the session-expiry signal ONLY when the 401 body carries a session-token code (`TOKEN_EXPIRED`/`TOKEN_INVALID`/`TOKEN_REVOKED`, emitted only by `server/middleware/auth.ts`) — never on a bare token-bearing 401; a route handler's own 401 (e.g. the account-delete password check) returns `UNAUTHORIZED` and must NOT log the user out. Expiry teardown is local-only — never POST `/api/auth/logout` (a dead token 401s → re-fires the interceptor, an expiry loop). See `docs/solutions/conventions/client-401-session-expiry-gating-and-local-logout-2026-05-30.md`.
- On ALL THREE teardown paths (`logout()`, `expireSession()`, `deleteAccount()`), BEFORE the state-clearing `setState`, clear every store in guarded (try/catch) steps, in order: (1) token + its `AsyncStorage` blob FIRST (in-flight work checks its send-time token on completion); (2) every durable replayed-later write store — offline mutation queue, draft/pending-upload list (`clear*` can't throw); (3) `queryClient.clear()`. If one path clears a store, all must: the query cache is keyed by query, not user (cross-user read leak); the write queue drains under the CURRENT bearer token (cross-account WRITE). See `docs/solutions/conventions/clear-query-cache-on-auth-teardown-2026-05-30.md`, `docs/solutions/logic-errors/durable-write-queue-not-cleared-on-auth-teardown-cross-account-replay-2026-06-19.md`, `docs/solutions/design-patterns/away-detection-focus-marker-and-unread-marks-in-query-cache-2026-10-01.md`.
- Multi-step flows that mutate server state AND sync local state either (a) atomically mark completion on the server step and rely on server idempotency, or (b) call `checkAuth()` / a server re-fetch in the catch when the server step succeeded but the local sync failed — never leave the user stuck behind a navigation gate after a server-side success.
- The global error net in `client/lib/query-client.ts` covers queries AND mutations (`MutationCache.onError`, 2026-09-25); both suppress 4xx (incl. `on401: "throw"` and 429), the mutation net also `AbortError`. Cache-level `onError` fires in addition to each observer's, so a query or `useMutation` with its own visible error opts out via `meta: { silentError: true }` (a mutation's `meta` is per-call — thread a `meta` param through a hook only when call sites disagree). The query net is the backstop — do NOT add a per-screen toast for query errors. `silentError` on a QUERY key is safe only when **every** consumer of that key opts out AND renders its own error UI — v5 stores `meta` on the shared cache entry (last `setOptions` wins), so a partial opt-out is mount-order-dependent; `findReferences` the **query key** (not the hook) first, and if any consumer relies on the global toast, accept the toast + inline double-report. Static keys (`QUERY_KEYS.dietaryProfile`, `["/api/daily-summary"]`) are the danger. See `docs/solutions/design-patterns/module-level-emitter-bridge-out-of-tree-to-toast-2026-05-28.md`, `docs/solutions/logic-errors/shared-query-key-meta-mount-order-2026-05-28.md`.
- When a screen reads a query, check `isError` **before** `data.length === 0` / `!data` — a failed query defaulted to `[]` otherwise slips into the genuine-empty branch. Render an error+retry state (e.g. `EmptyState variant="temporary"` with `onAction={refetch}`) distinct from first-run empty; for a 404-vs-transient split branch on `error.code === "NOT_FOUND"`, upgrading a bare-status query fn to a code-carrying `ApiError` via `throwStatusError` (`client/lib/throw-status-error.ts`) so mocked-`apiRequest` tests and production agree. A wrapper hook must itself expose `isError`/`error`. When a control's value derives from a fetched baseline AND a user action writes it back, a failed read MUST block the write path — render error/retry _instead of_ the controls, not just `disabled` gated on `isLoading` (`data?.x ?? default` masks a failed read as "empty" and a toggle persists a write against a phantom baseline). See `docs/solutions/logic-errors/read-failure-phantom-baseline-write-2026-05-28.md`.
- Every mutation surfaces visible failure copy in `onError` (toast, inline state, or equivalent) — haptics-only / VoiceOver-only handlers leave other users a silent no-op. Wrap every `await mutateAsync(...)` in `try/catch` — it rejects on failure and a hook-level `onError` doesn't suppress that rejection.
