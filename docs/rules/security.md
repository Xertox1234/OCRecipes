# Security Rules

> Binding directives only; embedded whole on every security-domain edit (cap: `scripts/check-rules-file-size.js`). Depth → `docs/solutions/best-practices/security-rules-extended-rationale-2026-06-05.md`. **Add new depth there, not here.**

- Ownership/visibility scoping (`isPublic OR authorId = userId`) lives in the SQL of EVERY storage fn taking a user-supplied id — reads AND writes (an unfiltered write binds a private resource to a user and leaks it on read). A single-resource read takes `userId` as a REQUIRED param and filters `id = ? AND (isPublic OR authorId = userId)` (keep the route check too); `authorId = NULL` is always false, so an empty `userId` fails safe to public-only.
- Polymorphic-FK junction inserts (`(parent_id, target_id, target_type)`) verify the TARGET's ownership/visibility with their own `EXISTS` guard — a parent-only guard scopes the wrong row; the resolve path hides non-visible-but-existing targets without orphan-deleting them.
- A batch id→metadata resolver scopes by the junction table that AUTHORIZES the caller (`INNER JOIN ... AND userId = ?`), never the resource's own `isPublic` flag (drops entitled-but-now-private rows and is no IDOR guard). Junction tables are append-only. Precedent: `getCommunityRecipeTitlesByIds`.
- A cross-user resource returns the SAME response as a missing one — never a distinguishable `403`: one guard `if (!x || x.userId !== req.userId)`; optional data resolves a cross-user hit to `undefined` and proceeds as if absent.
- Storage update fns take an explicit field whitelist — never `Partial<User>` or a spread of arbitrary input (mass assignment). Route bodies are Zod-validated (`schema.safeParse(req.body)`) before any field access. `req.userId` is a UUID string — never `parseInt` it (`NaN` silently bypasses ownership checks).
- Sanitize ALL prompt roles (`user`, `assistant`, `system`) at the OpenAI prompt boundary — never only `user`, never trust parameters that "look server-generated". Rate-limit every AI endpoint with a limiter from `server/routes/_rate-limiters.ts`.
- Safety/classifier regexes spanning newlines bound every `.*`/`[\s\S]*` gap, and a safety/injection detector's bound must be ≥ the upstream input-length cap (`[\s\S]{0,2000}` vs a 2000-char limit) — a smaller bound is itself a bypass. Routing-only heuristics may bound tighter.
- Premium-gate BOTH read AND write endpoints of a premium feature. Never index `TIER_FEATURES[tier]` with the raw stored `users.subscriptionTier` (not reset on expiry → lapsed users keep paid features): use `storage.getEffectiveTierForUser(userId)`, or `resolveEffectiveTier(tier, expiresAt)` (`@shared/types/premium`) only when you already hold a subscription record; never route per-request gates through the cached `resolveSubscriptionTierFeatures` (breaks route tests). B2B `ApiTier` has no expiry — never pass it through either.
- Legal attestation fields (age, ToS, marketing opt-in) thread from the UI checkbox through every hook to the API call — never hardcode `true` in an auth hook (the server gate still enforces, but the legal record is falsified). Consent/audit timestamps are stamped server-side from `new Date()` INSIDE the storage fn behind a boolean `recordConsent`-style flag (never a parameter; omit the column from the Zod schema and strip it from caller spreads) and are append-only: `COALESCE(existing, incoming)` in partial updates, existence guards in transactional upserts.
- `pull_request_target` workflows with repo secrets execute only trusted base-branch code — never checkout/source/import/install/execute PR-head files; fetch the PR head only as diff data.
- Behind a reverse proxy `app.set("trust proxy", <hop count>)` — numeric, NEVER `true` (leftmost XFF is spoofable) — and re-verify every `req.ip` consumer (rate-limit keying) on any topology change. A custom `keyGenerator` suppresses express-rate-limit's misconfig warning, so a collapse to one shared bucket (global lockout) is SILENT. Trust `X-Real-IP`/`CF-Connecting-IP` only when gated on the platform that overwrites them (e.g. `RAILWAY_ENVIRONMENT_NAME`).
- Never derive public-bucket/CDN object keys from user identifiers — `userId` IS exposed (`authorId` ships in community-recipe responses), so `sha256(userId)` is forward-computable. Runtime uploads: `crypto.randomUUID()`; idempotent migrations: mix in the content hash (`sha256(userId + ":" + sha256(bytes))`) or HMAC with a server secret.
- Bash scripts calling `psql`: validate any bare unquoted `:var` as a strict integer/keyword enum first (only `:'var'` is escaped — a bare value rewrites the WHERE clause or stacks a statement with no psql error), and never denylist a DB name by slicing the connection string (a query string, `?dbname=`, or percent-encoding defeats it; URL parsing is not enough) — denylist `SELECT current_database()` after connecting.
- Never auto-link a Google/Apple sign-in into an existing account that has a password — a verified email proves the inbox, not who chose the password; require the password (`link_required`). Only password-less accounts may auto-link.
- Sign-out clears state registered OUTSIDE the app too: unregister the device push token (the server reassigns a token to one user on register) and cancel OS-scheduled notifications — both outlive the session. Every `tokenVersion` bump also deletes the account's push tokens in its transaction: a phone whose session died server-side cannot send its own DELETE.
- A per-recipient send cap an unauthenticated caller can spend is never the cap recovery mail (reset codes, 2FA notices) spends — bucket a send by who can trigger it, not by its topic.
- IAP: `finishTransaction` only on body `success: true` (declines are 200); re-grant a `revoked` row only if the receipt's `purchaseDate` follows the revocation (no date fails closed).
